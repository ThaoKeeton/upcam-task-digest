## Contract and ownership

- API 1 and SDK assembly identity 1.0.0.0 remain; require host 0.2.0 and actual `IPluginRuntimeContext`. Plugin version remains the unreleased 0.1.0; standalone/core APP_VERSION remains 0.4.3.
- Register one `PluginBackgroundTask`, ID `digest-scheduler`, title `UPCAM 自动日报`, in Initialize. No worker, scheduling or network during initialization. Remove the private first-page scheduler; a page/manual operation may open the local backend but cannot create a scheduling loop.
- `RequiresPluginStart = false`: this application already has explicit saved automatic-send authorization and the user rejected per-run human review. Generic host Start is permitted only through the same callback which verifies that authorization. It never bypasses business validation. Host restore stays default off and must be explicitly chosen.
- Background delegate is returned/awaited by SDK, honors execution CancellationToken/StartReason/StopReason, and checks existing core run_due every 15 seconds. Stop/disable/shutdown must not leave an independent scheduling task. HostShutdown preserves opted-in restore intent; explicit task stop/disable follows SDK semantics. Unknown sends keep the existing ledger fence and never replay automatically.
- The local worker belongs to plugin/session lifetime, with the same standalone singleton and owned Job Object. Per-operation cancellation still kills an uncertain worker. Do not retain a completed user/task token as the worker session lifetime: link the client to plugin lifetime and use a temporary operation cancellation registration only during startup. A stopped scheduler must not later kill an unrelated manual operation. Plugin stop always closes its worker.

## Existing authorization proof, no service-key migration

Business API keys remain in the selected profile's existing Windows-user DPAPI store, the sole source used by Python and standalone rollback. Do not silently copy/dual-write them into host storage. Use the new SDK Secrets service for a generated schedule-restore binding key instead, with a visible explanation of this scope.

- Register `PluginSecretDefinition("upcam.resume-binding-key", "日报自动恢复校验密钥", ...)`. Generate 32 random bytes/base64 only after an explicit UserRequest start has passed local business authorization. Never generate on Restore, never show/log/return its value, never pass it as a child argument or into host JSON.
- Persist only non-secret binding metadata in host Settings key `schedule-binding-v1`: schema 1, canonical profile directory, and an HMAC-SHA256 proof. Message is canonical profile + newline + authorization_fingerprint from the backend. Use constant-time comparison. Host Secrets unavailable/corrupt means safe background-start failure; no plaintext fallback.
- New adapter operation `plugin_auto_authorization`, empty payload, requires handshake. It requires saved auto_send_enabled=true and invokes the existing WorkerService local auto-ready validation (scope proof, credentials, model cache/capability, robot configuration, ledger) without any service request. Return `{authorized:true,authorization_fingerprint:<64 lowercase hex>,data_directory,application_version,ruleset_revision}`. Fingerprint hashes canonical profile, rules revision, all non-UI business settings, and a hash of relevant service/internal ledger credentials; no values or internal ledger ID escape.
- UserRequest callback validates and stores a fresh binding. Restore reads the existing generated key/binding and freshly validates the same saved business authorization before any collection/model/send. Missing/mismatched binding, changed scope/keys/schedules/settings or unready credentials faults/stops safely; it must not mint replacement authorization during restore.
- Revalidate the binding before each due check, then call plugin-only `plugin_run_due_authorized` with exactly the expected `authorization_fingerprint`. Inside that operation, take one validated settings and credential snapshot, compare its fingerprint in constant time, and use the same immutable snapshot for due-slot selection and workflow construction. Reject stale proof before any client, model or sender is constructed; never delegate this automatic path to independently reloading ordinary `run_due`. Standalone behavior and the original ledger remain unchanged. No authorization requirement is replaced by the HMAC.

## Native controls and changes

- Provide native start/stop/status and explicit host-startup resume setting using real BackgroundTasks APIs; platform management pages may still be unfinished, so plugin controls/commands must be usable themselves. No fake unavailable global controls.
- Explicit successful business Save may start the host task when saved automatic sending is true. It cannot opt into startup restore unless the user explicitly changes that separate option. Auto off, clear credentials and profile switch stop the host task; profile changes clear host resume preference/binding before adopting a new scope. Keep the original DPAPI preferences/data for standalone rollback.
- Stop a managed background execution before acquiring the session gate for profile switch or relevant business Save, to avoid waiting behind a two-hour collection. Preserve per-profile dirty drafts. A persistence/stop failure is reported truthfully and cannot be treated as a successful migration.
- Fence configuration transitions before stopping tasks; callbacks must reject changed authorization generations and cannot mint a binding during a transition. Plugin start may report the host's accepted request without waiting on an unowned callback completion; actual running/readiness remains visible separately. Published lifecycle stop reasons plus plugin-lifetime cancellation complete cooperatively, including when execution-token cancellation arrives later.
- Preserve foreground feedback/editor focus during background checks. Runtime snapshots may refresh native status locally without business requests or tree replacement. Last operation errors remain actionable and secret safe.
