# 更新时间候选优化：范围与验证

## 根因与选择

`f65d430` 为防止“窗口内有动态、窗口后再次更新”的任务漏采，移除了旧 `updated >= start AND updated < end` 查询。其副作用是对项目内每个任务都读取详情和全部历史动态。分批采集只延长了可处理范围，没有减少这部分请求。

当前默认策略：

1. 完整分页列出当前可读项目任务，保持原归档选项、1 万任务上限和所有预算。
2. 先校验每行身份、项目、归档和带时区的 `updated`，再在本机选择 `updated >= start - 24h`。
3. 对候选任务读取详情及全部动态页，不遇到旧动态就提前结束。
4. 最终仅按动态 `createTime` 的原半开窗口 `[start, end)` 生成日报，保留窗口后的状态/负责人/位置链核对。
5. 完整重列任务并重新选择候选，刷新新增或变化的候选，最多三轮；仍不稳定就阻断，不返回部分结果。

没有任务更新时间的结束上界。开始前 24 小时只是固定的保守重叠，覆盖已见毫秒级不同步；不保证任意时间偏差或任意动态类型的覆盖。

## 明确的局限

官方资料没有证明所有动态都会推进任务 `updated`。旧任务若出现新动态但更新时间仍早于下界，默认快速模式就可能遗漏。全列表重核、重叠、并发和缓存都不能消除这一限制。快速模式不承诺完整历史覆盖，`activity_updated_index_guaranteed`、`historical_event_coverage` 和 `snapshot_guaranteed` 均为 false。

需要不按更新时间排除旧任务时，用 `Client.collect(..., candidate_mode="full_project")`。原生“详细诊断导出…”固定采用此模式，只读取 Teambition 并写入用户选定的私有文件，不调用 OpenAI 或发送钉钉。普通只读诊断与日报使用默认候选模式。全量模式仍受可见项目、归档选项和预算限制，不能恢复已删除、不可见或已移出项目的历史任务。

两种规范合同都可被当前报告/发送验证器读取，v0.4.1 的双边界选择合同仍被拒绝。旧历史不迁移、不删除。采集进度绑定整个规范合同，切换策略时不复用任务缓存。

## 合成验证

运行 `python -m unittest discover -s tests -v`。所有服务均为虚构数据和替身传输，本变更没有访问真实 Teambition、OpenAI、Webhook 或钉钉。

`tests/test_candidate_prefilter.py` 验证：

- 项目 1,200 项，仅 12 项满足候选下界，详情/动态仅请求这 12 项。两轮完整列表共 24 次请求，详情和单页动态共 24 次，总计 48 次；原全项目历史扫描是 2,424 次。该结果是可重复的请求数量比较，不是真实网络耗时保证。
- 列表分页仍完整且没有 `q`；省略候选的列表行仍受内存、项目数量和分页完整性检查。
- 下界包含等号、UTC 等价时刻、开始前微小偏差、窗口后再次更新；不存在任务时间的结束上界。
- 原活动半开边界不因候选重叠而扩大，历史页不因全为旧动态提前停止。
- 时间/项目/归档无效的列表行即使本应被过滤，也会阻断。
- 结束复核发现新近更新的任务会重新读取；快/全策略的缓存不互用。
- 测试明确展示未推进 `updated` 的旧任务在快速模式中会被跳过，而全量模式会读取其动态，防止把优化误写成完整性保证。
- 旧全量合同仍可验证，篡改候选下界等合同字段会被拒绝。

另有工作进程回归确认详细导出确实选择全量模式，且保留原有私有导出和“不摘要、不发送”边界。

## 后续服务端 q 评估

当前刻意不启用 `q`，所以列表请求数不减少。下一步若要减少它，必须先核对官方语法和时区/比较精度，再以同一固定数据样本比较 `q=updated >= cutoff` 与无 `q` 全列表的本机结果，并覆盖分页、归档、空结果和不支持查询时的行为。不得恢复 `updated < end`，也不得把一次对比视为所有动态都会改变 `updated` 的证据。当前未进行真实 API 比较，不能宣称该服务端优化已验证。

官方查询参考：[项目任务查询](https://open.teambition.com/docs/apis/6321c6d1912d20d3b5a49ec1)、[Teambition 官方 TQL 参考](https://github.com/teambition/tb-skills/blob/main/dingtalk-teambition/references/tql.md)。这些资料说明更新时间查询/比较语法，不构成全部动态推进更新时间的保证。
